# Security — PROVING GROUND

PROVING GROUND sends ten known, harmless test calls through your installed Hermes plugins inside a throwaway child Hermes home, with the model never called. This page lists what it enforces, what it does not defend against, and which test checks each invariant. A report describes what your plugins did with these synthetic inputs; it does not grade your stack.

## Threat matrix
| # | Threat | Enforcement | Where |
|---|---|---|---|
| T1 | The scripted-turn middleware runs in your live session and drives real tool calls in your cwd | Triple-key activation (env token, matching token file, `<temp>/provingground-XXXXXXXX/home` path shape). The path key can never hold for `~/.hermes`. The middleware is registered only in `_register_drill_child`, with no fallback path | `__init__.py`, `proving_ground/safety.py` |
| T2 | The injector errors, middleware fails open, and a real provider is called | Whole middleware body wrapped; scripted `DRILL_ABORTED` reply; dead `127.0.0.1:9` model endpoint; no provider keys in the child env | `proving_ground/injector.py`, `proving_ground/runner.py` |
| T3 | Another plugin rewrites a test call to land outside the temp dir, or a replayed or user-supplied call carries an unsafe command | Child HOME/TMPDIR/cwd/XDG inside the temp root, dead proxies, Hermes's approval floor after rewrites; ESCAPED is detected on the final args after it ran (not prevented), then `ABORT` plus a process-group kill. Cross-check replays and `--calls` files must pass a closed allow-list grammar; a call that fails it is never executed | `proving_ground/observer.py`, `proving_ground/runner.py`, `proving_ground/testcalls.py` |
| T4 | PROVING GROUND's own scripted call leaves the temp dir (template edited) | `testcalls.render` refuses it; PG's own `pre_tool_call` blocks it (`INJECTED_OUTSIDE_SANDBOX`) | `proving_ground/testcalls.py`, `proving_ground/observer.py` |
| T5 | A test call uses a tool whose direct-call path has a different hook order | Allow-list `terminal, write_file, read_file, patch` in the loader and in `pre_tool_call` (`TOOL_NOT_ALLOWED`) | `proving_ground/safety.py` |
| T6 | Approvals auto-resolve to approve in the child | Child config forces `approvals.mode: manual` with `cron_mode`/`single_query_mode`/`unattended_mode: deny`; the env allow-list drops `HERMES_YOLO_MODE`; argv never has `--yolo`/`-z`/`--oneshot`; no approval transport is registered | `proving_ground/runner.py`, `tests/test_approvals_static.py` |

| T10 | An orphan child, daemon or temp root survives, or the sweep deletes a directory PG did not create | `start_new_session` + killpg; env-matched daemon kill after every column; nested `finally`; SIGINT/SIGTERM/SIGHUP cancel queued and in-flight columns; the stale sweep deletes only exact 8-char roots with a parseable `.pg-root` marker and a dead pid | `proving_ground/runner.py`, `proving_ground/safety.py` |
| T11 | The catalog scanner flags the plugin | No secrets, no provider prefixes, no injection phrases, no destructive shapes, no encoding; `testcalls.yaml` at the repo root at full severity; CI runs validate | `testcalls.yaml`, `.github/workflows/validate.yml` |
| T12 | A misleading report creates false assurance | Fixed wording and a forbidden-claims check on every format, a drill-conditions box, LOAD FAILED and N/A distinct from PASSED THROUGH, INCOMPLETE aborts, ERRORED for raising hooks, UNSTABLE exclusion, a coverage line | `proving_ground/report.py`, `proving_ground/matrix.py`, `tests/test_report_wording.py` |
| T13 | A report reveals what a stack does not stop, or this machine's paths | Stored locally by default; exported only by an explicit flag; home and temp paths replaced by `~` and `{TMP}` in saved and exported reports; no telemetry | `proving_ground/cli.py`, `tests/test_report_loading.py` |
| T14 | HTML report injection from plugin output | Every dynamic string goes through `html.escape`; no scripts | `proving_ground/report.py` |

## Not defended against
- **Another plugin's own in-process network code** during a drill. A plugin cannot block another plugin's sockets. The socket audit records connects made from the child Hermes process, and only synthetic data is present.
- **Absolute-path writes or reads by another plugin's own code** (not through a tool call) outside HOME and the sandbox. The env redirection covers `~`, XDG and TMPDIR, not arbitrary absolute paths a plugin hard-codes; it is not an OS sandbox. Disclosed. OS-level confinement (`sandbox-exec` / `bwrap`) is not implemented.
- **A tool call that escapes before PG sees it.** ESCAPED is recorded in `post_tool_call`, after execution: detected after it ran, not prevented.
- **A subject `tool_execution` middleware that skips the dispatch.** Execution middleware wraps Hermes's authorized dispatch, which is where every `pre_tool_call` runs, PG's sandbox pin included (Hermes `agent/tool_executor.py:776-818`). A subject frame that returns without calling `next_call` skips that pin, and whatever that plugin's own code does instead is not seen by any hook. PG loads innermost and records the call as EXECUTION REPLACED from `post_tool_call`, where the final args are still checked for ESCAPED: detected after it ran, not prevented.
- **Hooks and middleware the drill does not reach.** The report lists, per plugin, what it registered and what fired; a hook listed as never fired (UNTESTED) was not exercised by these test calls, and registered tools and commands are never exercised. A subject that loads after PG (a `requires_plugins` layer) has its `llm_execution` middleware inside PG's scripted frame, where it does not run; the report says so for that plugin.
- **launchd user-domain environment** (`launchctl setenv`): on macOS each child home's gateway runs as a one-off launchd job whose plist carries the child's allow-listed environment (Hermes `gateway_launchd_runtime.py:117-127`). launchd may add variables you set yourself with `launchctl setenv` to that job, and PROVING GROUND does not remove them. The drill's approvals do not depend on that environment: the child config forces manual approvals with single-query, cron and unattended modes on deny. `launchctl getenv HERMES_YOLO_MODE` shows whether you have set one; it was empty on the machine the committed reports come from.
- **A session-level `/yolo` toggle** in the user's live session. Its check (`tools/approval.py:579`) is not a public API. PG refuses on env and config only; a Hermes issue asking for a public check is drafted (not yet filed).
- **A malicious local user** who forges all three activation keys in a temp dir of their own. They already control the machine; the keys exist to stop accidental activation, not a local adversary.
- **Stateful or time-dependent plugins** whose behaviour differs between solo and stack runs for reasons unrelated to interaction. They can produce an `interaction` attribution; the report says "appears only in combination", not "caused by combination".

## Disclosure
> **Disclosure — what PROVING GROUND does on your machine**
> - **Starts Hermes child processes.** Each check runs `hermes chat -q` as a subprocess with its own temporary Hermes home, home directory and working directory, all under your system temp directory. Its tests check that your real Hermes config, sessions, memories, state database, SOUL.md and installed plugins are unchanged by a drill; reports go to `plugin-data/proving-ground/`. The children and their temporary files are deleted when the check finishes or is interrupted (SIGINT, SIGTERM, SIGHUP).
> - **Leaves Hermes's own launchd job labels on macOS.** On macOS each child home's gateway runs as a one-off launchd job in your GUI domain. After the drill no process is left, but the finished job labels stay listed in `launchctl list` until Hermes's next gateway start removes them (Hermes `gateway_launchd_runtime.py:91-97`). launchd may also add variables you set yourself with `launchctl setenv` to those jobs' environment; PROVING GROUND does not remove them (`launchctl getenv HERMES_YOLO_MODE` shows whether you have set one).
> - **The parent `hermes` process may write Hermes's bytecode.** The stock `hermes` launcher runs Python with `-I`, which ignores `PYTHONDONTWRITEBYTECODE`, so the `hermes` process you start may write `.pyc` files into your Hermes install. That is Hermes's own behaviour. Every drill child runs Hermes's interpreter with `-B` and its report says bytecode was off.
> - **Installs an audit hook in each drill child.** The child process calls `sys.addaudithook` to count connects to addresses outside loopback (the report's network line). Python audit hooks are process-wide and cannot be removed; the hook only exists inside the throwaway child, never in your session.
> - **Watches your plugins' callbacks in each drill child.** Inside the throwaway child only, each subject plugin's registered hooks and middleware are replaced by pass-throughs that note when they fire and then call the plugin with exactly the arguments Hermes would have given it (Hermes's own argument narrowing). PROVING GROUND reads which hooks, middleware, tools and commands each plugin registered from Hermes's plugin registry, read-only. Nothing of this happens in your session.
> - **Your plugins run with your permissions.** The child home is a throwaway directory, not an OS sandbox. Subject plugin code runs with your own file permissions; a call rewritten to land outside the temporary directory is detected after it ran, not prevented, and the column is stopped.
> - **Prepares a runtime cache once.** On first use, after saying so in one line, it copies Hermes's runtime from your own Hermes installs dir (the current Hermes home's `installs`, else `~/.hermes/installs`) into `<temp>/provingground-cache` (mode 0700, refused if it belongs to someone else or is a symlink). The source is only read, no network is used, and the copy must start (`hermes --version` in a throwaway home) before it is used; a copy that does not start is removed. Only when there is nothing to copy, or the copy is refused, does one child let Hermes's own installer download the runtime (about 650 MB), exactly as it does for any new Hermes home. The slash command never downloads. Later checks point every proxy at a closed local port.
> - **Finds and stops its own children.** After each column it runs one `ps axeww` scan, which prints every process's command line and environment. It keeps, in memory only, the lines of processes whose text mentions hermes or python, matches them on an exact `HERMES_HOME=` word naming one of its own temporary homes, and sends those SIGTERM/SIGKILL. It deletes only temporary directories that carry its own ownership marker.
> - **Posts into your chat after a slash drill.** When `/provingground` finishes in the background, it posts the drill's summary into the session that started it with Hermes's `post_message`; nothing is posted anywhere else.
> - **Sends synthetic tool calls through your installed plugins.** Inside the child the model is never called. A fixed, readable list of ten harmless test calls (`testcalls.yaml`) goes through Hermes's normal tool path: file writes, reads and patches inside the temporary directory, and short shell commands that only print, write test markers inside it, or fetch from PROVING GROUND's own local recorder. Your plugins see these calls exactly as they would see real ones.
> - **Approvals stay on and are always denied.** The child runs with approvals forced to manual and every headless approval denied. PROVING GROUND never answers, approves or hides an approval, registers no approval transport, and refuses to run when YOLO, `approvals.mode: off`, cron or a messaging platform is active.
> - **No network calls of its own.** It opens one local listener on `127.0.0.1` (random port) to record whether a test call reached execution. The children have no API keys or credentials, and their model endpoint is a closed local port. PROVING GROUND cannot stop *other* plugins from making their own network calls during a check. Those plugins would see only synthetic data.
> - **Reads outside its own data:** your Hermes installs dir when the runtime cache is cold (read-only, copied as above), your enabled-plugin list, those plugins' directories and their `plugins.entries` settings (read-only, copied into the temporary child). Credential-shaped files (`.env*`, `*.key`, `*.pem`, `auth*.json`, …), symlinks leaving the plugin dir, secret-shaped settings and token-shaped values are withheld from the copy, and the report lists them. It never reads `.env`, `auth.json` or any credential store of its own accord. An optional `--calls FILE` you pass is read and validated.
> - **No telemetry.** Reports are written to PROVING GROUND's own plugin-data folder and shared only if you export them. Saved and exported reports replace your home and temp directory paths with `~` and `{TMP}`.
> - **What a report means:** it shows how your plugins treated these specific synthetic inputs in a sandbox. It does not grade your stack.
> - **Rule 12 (spawned children).** The child is a single-query `hermes chat -q`, but its config forces approvals to manual with single-query, cron and unattended modes all on deny, it never gets `--yolo`/`-z`/`--oneshot` or `HERMES_YOLO_MODE`, and the only commands it runs are the listed calls in `testcalls.yaml` (plus your own `--calls`, which must pass a closed grammar). Anything approval-worthy is denied by Hermes itself.

## Invariants and their tests
| # | Invariant | Test |
|---|---|---|
| I1 | Drills run only in a child process with a throwaway Hermes home; the live session registers no scripted-turn middleware | `tests/test_arming.py` |
| I2 | Every test call's paths and hosts stay inside the temp root and PG's own loopback recorder | `tests/test_containment.py` |
| I3 | A rewrite that leaves the temp root is detected on the final args and the column is stopped (ESCAPED) | `tests/test_containment.py`, `tests/test_escape_abort.py` |
| I4 | Approvals stay on and always deny in the child; PG never answers, approves or hides one | `tests/test_approvals_static.py`, `tests/test_child_spawn.py` |
| I5 | PG refuses to start a drill when your posture bypasses approvals or nobody is present | `tests/test_posture.py` |
| I6 | Child Hermes processes connect only to loopback; PG makes no network calls of its own | `tests/test_network_loopback.py` |
| I7 | Your real Hermes config, state DB, SOUL.md, memories, sessions and installed plugins are unchanged by a drill | `tests/test_home_untouched.py` |
| I8 | Interrupts and crashes leave no child, daemon or temp root behind | `tests/test_cleanup.py` |
| I9 | Only the four allow-listed tools are used, through one validator for built-in and user calls | `tests/test_testcalls_schema.py` |
| I10 | No report format grades the stack | `tests/test_report_wording.py` |
