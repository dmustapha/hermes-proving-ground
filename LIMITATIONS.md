# LIMITATIONS — what PROVING GROUND does and does not do (v0.1.1)

## In scope
- **Directory plugins enabled in your Hermes home** (`<HERMES_HOME>/plugins/<key>/`), tested one at a time and all together against a zero-plugin baseline.
- **Twenty executed synthetic test calls** using four tools (`terminal`, `write_file`, `read_file`, `patch`), all inside a temporary sandbox: prints, sandbox file writes/reads/patches, one loopback fetch from PG's own recorder, one approval-worthy permission change that headless approvals deny, output shapes printed with `printf` (ANSI colour, a carriage-return progress bar, duplicate lines, a base64-looking line, minified JSON, AWS's documented example key id), and home-shaped files inside the sandbox (`.env` and `.ssh/id_rsa` seeded with synthetic text, a `.bashrc` and a `config.yaml` written).
- **Four block-only probes** (TC21-TC24: `execute_code`, `delegate_task`, `web_extract`, `memory`). PROVING GROUND's own `pre_tool_call` blocks each one in every column, so none runs; a plugin's block or rewrite of the call still shows. Cells read NOT EXECUTED (probe) when no plugin acted first.
- **The turn-stop gate** (`pre_verify`): a plugin's nudge after the drill's file edits shows as TURN EXTENDED on the edits it followed.
- **Six outcome classes plus four status classes:** BLOCKED, REWROTE, RESULT CHANGED (hop named), APPROVAL-GATED, PASSED THROUGH, ESCAPED; ERRORED, LOAD FAILED, NOT RUN, N/A.
- **Attribution** by solo runs (`solo-match`, `multiple-candidates`, `interaction`, `core`) and the **REWRITE_UNSEEN_BY** cross-check.
- **Hermes v0.23.1** on **macOS** (verified) and **Linux** (verified in CI: the `linux-drill` job on ubuntu-latest installs PROVING GROUND from git, runs `hermes provingground --fixtures` with TMPDIR unset and checks the golden matrix and zero leftovers; run 42994971722). The manifest declares `platforms: [macos, linux]`. With TMPDIR unset, Hermes points the temp dir at `<HERMES_HOME>/cache/scratch`; drills then use the first existing system temp dir (`/tmp` on Linux) instead.
- **Surfaces:** `hermes provingground` (run/show/lock/diff/warm/sweep) and `/provingground` from the CLI, TUI, Desktop or local sessions.
- **Reports:** terminal, Markdown, self-contained HTML, JSON; stored locally.

## Feature-gated or not covered (with reasons)
| Limitation | Reason | What PG does instead |
|---|---|---|
| Rewrites and escapes are **detected after they ran, not prevented** | no plugin seam sees final args before execute (`hermes_cli/plugins.py:1132-1150`) | environment containment + ESCAPED stop; no pre-execution pin is claimed |
| **ASKED** cells (a person asked) exist only in `--attended` runs | headless children can't ask; PG never answers approvals (rule 12) | a default drill shows APPROVAL-GATED (Hermes denied it headless); `--attended` shows Hermes's own prompt and records the person's answer |
| Session-level **`/yolo`** toggle not detected | `is_approval_bypass_active_for_session` is not a public API (`tools/approval.py:579`) | refuses on `HERMES_YOLO_MODE` and `approvals.mode: off`; Hermes issue drafted |
| **pip / entry-point plugins** are not tested | they have no plugin directory to copy into the sandbox | listed under "skipped" with the reason |
| Plugins that declare **`requires_env`** are not run | the sandbox has no credentials by design | column shows N/A with the reason |
| **Other plugins' own network code** can't be blocked | a plugin cannot block another plugin's sockets | dead proxies, no credentials, synthetic data only; the socket audit counts connects from the child Hermes process (not from subprocesses such as the terminal tool's commands) |
| **Absolute-path writes** hard-coded by another plugin (outside a tool call) | HOME/XDG/TMPDIR redirection doesn't cover arbitrary absolute paths | disclosed; the real-home hash test guards Hermes's own files |
| **Messaging platforms** for `/provingground` | v1 is for attended local surfaces | `REFUSED_PLATFORM` |
| **Windows** | process and temp-path handling not built for Windows | `SANDBOX_UNSUPPORTED` |
| A **`TMPDIR` outside the system temp bases** (`/tmp`, `/var/tmp`, `/var/folders`), e.g. nix-shell or `$XDG_RUNTIME_DIR` | drill roots are only created under a system temp base | `SANDBOX_UNSUPPORTED`, naming the remedy: run with `TMPDIR=/tmp` |
| **Context / reply hooks** (`pre_llm_call`, `transform_llm_output`) are recorded only with `--all-wires` | a default drill tests the tool path only | `--all-wires` adds an LLM-CONTEXT and an LLM-REPLY row; the context row compares the system prompt, user turn and tools offered with the baseline's, so a plugin's system-prompt section shows there too |
| **Stateful or time-dependent plugins** may differ between runs | each column is a fresh process | the baseline-repeat check marks unstable calls (`~`); stack-only effects are labelled `interaction`; `--repeat N` runs the solo columns with an effect again and marks disagreeing cells UNSTABLE; `--pairs` looks for the smallest set behind an `interaction` |
| **First run** needs the runtime once: a copy of your own Hermes installs (no network), else a ~650 MB download | Hermes's own runtime install for a new home | the first drill or `warm` copies it from your Hermes installs when there are any (the source is only read, the copy is checked to start); otherwise one download, announced in one line, with its own 15-minute limit; a failed warm-up refuses the drill (`WARMUP_FAILED`); `warm --status` reports readiness; later drills use dead proxies |
| The warm cache lives under the **temp directory of the shell** | it is `<temp>/provingground-cache`, so a shell with another `TMPDIR` (or macOS's periodic temp cleanup) finds it cold | `hermes provingground warm --status` names the cache path for the current shell |
| **Finished launchd job labels** remain on macOS (no process) | Hermes's gateway on macOS starts a one-off launchd job per child home | Hermes removes finished labels at its next gateway start (`gateway_launchd_runtime.py:91-97`); PG leaves no running process; disclosed in SECURITY.md |
| A plugin storing a **secret in `plugins.entries`** has it copied into the temp child | PG copies plugin settings so plugins behave as configured | the child is deleted after the column; rule 11 says secrets belong in Hermes's secret routes, which PG never reads |
| Only **Hermes 0.23.1** tested; floor declared `>=0.23.1` | the build machine runs 0.23.1 | seams cited by file:line; re-test on upgrade |
| The **parent `hermes` process** can write Hermes's own bytecode (`.pyc`) into your Hermes install | the stock launcher runs Python with `-I`, which ignores `PYTHONDONTWRITEBYTECODE`; that is Hermes's launcher, not PG | every drill child (and the `--version` probe) runs Hermes's interpreter command with `-B` and reports bytecode off; to keep the parent from writing too, run PG from a launcher copy that adds `-B` |
| **User calls are a closed grammar** | User terminal calls are a closed grammar: `echo` or `printf` whose first word is not a flag (later words, flags included, are printed, never run), `seq` without flags (at most 20000 lines), `curl -q` to the run's own recorder, and `chmod` with a 3-digit octal mode that keeps the owner's read and write on sandbox paths below the sandbox root; no pipes, `;`, `&`, `$`, redirection, globs, `..` or `~`, no `printf` `%n` or width over 9999, and only the argument names the tool needs (`command` for `terminal`; no `background` or `workdir`). Write your trigger as text your guard matches, e.g. `echo git push --force`. | a call outside it is refused before any drill, with the reason |
| A **hard kill** (`kill -9`, a crash, a closed terminal) skips cleanup | no process can clean up after its own SIGKILL; on macOS a child gateway's launcher can outlive it, reparented to PID 1 | the next drill or `hermes provingground sweep` stops every process whose environment names a dead drill's exact `HERMES_HOME`, then removes its root; Ctrl-C, SIGTERM and SIGHUP clean up at once |
| **Relative paths and `~`-named seed files are not refused in user calls** | the child's working directory is the sandbox, so a relative `path` stays inside it; a seed key starting with `~` or `/` is refused | write `{SANDBOX}/name` for clarity |
| **User calls print flag-shaped words, they never run them** | the closed grammar allows `echo`/`printf` only, so `echo git push --force` reaches every `pre_tool_call` as a terminal command whose text has the shape a guard matches; the command itself only prints; Hermes's own dangerous-command check matches the printed text as well (`tools/approval_detection.py:660`), so such a call is APPROVAL-GATED (core) in every column a guard does not block | a guard keyed on the shape fires; one keyed on the program actually running, its exit code or its side effects does not |
| **Home-shaped paths live in the sandbox, not the child's HOME** | every test call must stay inside the sandbox (containment), so `.env`, `.ssh/id_rsa`, `.bashrc` and `config.yaml` sit under the sandbox directory | a plugin matching the path shape or the file name sees them; one that resolves `~` or `$HOME` and compares exact paths does not. Hermes core refuses the `.env` read and masks the key block itself, so a plugin's own redaction there shows only if it differs from core's |
| **Block-only probes: a plugin's approve is hidden** | the first block in load order wins (`hermes_cli/plugins.py:1132-1160`), so a plugin's `approve` on a probe is always hidden (block beats approve); PROVING GROUND's copy loads last (`runner.child_pg_key`), so every subject's block shows, except a subject with `requires_plugins`, which loads in a later layer after it | the probe cell's note says so; rewrites (modify) show whatever the order; a drill with a guard keyed after `proving-ground` shows its block as BLOCKED (`tests/test_coverage_calls_e2e.py`) |
| **Probe tools must be offered** | Hermes rejects a tool name outside the enabled toolsets before any hook (`agent/turn_tool_round.py:60,122`); the child enables the four probe toolsets, but a tool whose own availability check fails is not offered | the probe cell reads N/A with that reason |
| **Reply and user-turn probe text is synthetic** | `wire_probe` in `testcalls.yaml` holds synthetic PII, a test DOI, CJK and Cyrillic text and a repeated token; every drill appends it to the scripted prompt and final reply | a reply or user-turn plugin acts on these shapes only; a plugin keyed on other text shows PASSED THROUGH. The --all-wires rows quote it |
| A **green matrix is not a grade** | 24 synthetic inputs cannot cover a stack's behaviour | the wording is fixed: "Observed on N synthetic inputs in a sandbox" |

## Known gaps, with reasons
| Item | Status | Reason / what to do |
|---|---|---|
| **The child is not an OS sandbox.** Subject plugin code runs with your file permissions and can read files by absolute path | disclosed | OS-level confinement (`sandbox-exec`/`bwrap`) is not implemented; the README Safety model and the SECURITY.md Disclosure say so |
| **Each plugin runs in one solo run** by default; stateful plugins (counters, budgets, rate limits) can differ between runs and with call order | disclosed; `--repeat N` repeats on request | a repeat run of every solo column costs drill time, so it is opt-in and only covers the solo columns with an effect; attribution text says "observed in one solo run" |
| **Bundled / default-on Hermes plugins in the baseline are not enumerated** | disclosed | no public seam lists every loaded plugin; `has_plugin` only answers for known keys. Conditions line: "bundled plugins not enumerated" |
| **launchd user-domain env** (`launchctl setenv`) can reach the macOS gateway job | disclosed | launchd may add variables you set with `launchctl setenv` to each child home's gateway job; PG does not remove them. The drill's approvals come from the child config (manual, every headless mode on deny), not that environment. `launchctl getenv HERMES_YOLO_MODE` shows whether you have set one |
| **`python_dependencies` of real plugins** are not in PG's shared runtime cache | reported as LOAD FAILED | the plugin cannot import in the child; the column says so instead of passing |
| **Plugin names are user-chosen text** | partial | the forbidden-word check exempts quoted plugin output, not plugin *names* in findings; a plugin named e.g. `safe-x` would trip the development-time check (reports still render) |
| **`ps axeww` inspection** of every process's environment | disclosed, narrowed | one scan per cleanup prints every process's environment; only the lines that mention hermes or python are kept, in memory, and matched on PG's own HERMES_HOME needle; launchd labels are not matched |
| **Credential-shaped file names** are a heuristic | partial | `.env*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `auth*.json`, `credentials*`, ssh key names, `secret(s).json/yaml/toml` are withheld; other names are copied |
| **Per-plugin liveness is unknown** | by design (catalog rule 9) | PROVING GROUND uses only public plugin APIs (`register_hook`, `register_middleware`, `has_plugin`) and never reads or rewrites the plugin manager's private state (`_plugins`, `_hooks`, `_middleware`). So a PASSED THROUGH cell does not say whether a plugin ran on the call and changed nothing, or was never invoked, and the report does not list which registered hooks fired. Load order is the one computed from the manifests (`requires_plugins` layers, then alphabetical), the order Hermes uses. A public read-only dispatch trace in Hermes would let this come back |
| **Saved reports are pruned** | by design | `plugin-data/proving-ground/reports` keeps the newest 20 `report-*.json` files (plus `latest.json`); older ones are removed when a new report is saved. Export a report with `--json` to keep it |
| **Column times vary with machine load** | measured, not a PG delay | one earlier verification run saw a 57 s solo column (1 of 5 runs). It did not recur in 11 later fixture drills on the build machine (2026-11-11, load average 15-19 from other work): drill walls 24.6-47.6 s, slowest column 22.8 s. Per column, Hermes's start up to PG's activation took 2.2-10.2 s, the scripted turn 2.6-12.0 s, and the child's exit after the turn 0.2-0.5 s, so the gateway daemon and launchd did not hold a column open. When a wave was slow, all five parallel columns were slow by the same amount, which points at the host, not one plugin or PG. Each column has a 120 s limit (`--timeout`) with one retry, and a column that still overruns is reported CELL_TIMEOUT |
| **The measured-home claim** covers config, state DB, SOUL.md, memories, sessions and plugins only | narrowed claim | logs/ and other Hermes-owned files written by the parent `hermes` process are not claimed |
